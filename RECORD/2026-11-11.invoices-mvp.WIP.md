# Invoices MVP

Roadmap tasks `a2`, `a3` and the start of `u1` of [`ROADMAP/2026-11-11`](../ROADMAP/2026-11-11/README.md). Follows [`2026-11-11.foundations-repo-ci-csp`](2026-11-11.foundations-repo-ci-csp.WIP.md).

## 2026-11-11: Chained records, invoices API and first UI

Author's instructions: run jq79 precompiled; build whatever gets closest to the MVP.

Done:

- `crates/core`: record hash for registration and cancellation records, checked against the three examples of the AEAT hash specification; invoice validation and totals (line bases rounded to cents, tax computed per VAT rate, half away from zero); QR URL.
- Migration `0001`: `invoices`, `invoice_lines`, `invoice_taxes`, `billing_records`. All insert-only: triggers reject `UPDATE`, `DELETE` and `TRUNCATE`; role `vericounts_app` only has `SELECT` and `INSERT`. `UNIQUE (issuer_nif, previous_hash)` prevents forks.
- `vericounts-server migrate` applies migrations (owner role); `serve` runs with the restricted role.
- API under `/api`: `POST /invoices/preview`, `POST /invoices`, `GET /invoices`, `GET /invoices/{id}`, `POST /invoices/{id}/cancellation`, `GET /chain/verification`. Numbering and chaining run in one transaction under an advisory lock per issuer.
- Integration tests on real Postgres (`#[sqlx::test]`): chaining, cancellation, validation, 12 concurrent creations, immutability for owner and app role, tamper detection. CI has a Postgres service.
- Web client in `web/` (Vite + `jq79@0.7.11` with `safeEval: true`): list, new invoice with server-side preview before issuing, detail with records and QR link, cancellation. Checked in headless Chromium (mobile viewport) against the real server and CSP: no console errors.

Decisions taken, pending confirmation by the author:

- Vite is used for precompilation (the supported jq79 path for `script-src 'self'` without a service worker). The server serves `web/dist`.
- Trusted Types: the CSP now allows the `default` policy. `web/src/trusted-types.js` lets HTML sinks through (jq79 needs `DOMParser` and `innerHTML`), refuses script text and only accepts same-origin script URLs. A named policy inside jq79 would let the CSP be stricter.
- Queries use runtime-checked `sqlx::query`, not the compile-time macros, to keep builds independent of a database.
- Invoice number format: `<series>-<number, 4 digits>`; series is `A-Z0-9`. Numbers are per series and gapless; an invoice cannot be dated before the last one of its series nor in the future.
- Only invoice type `F1` and VAT rates 21, 10 and 4. No exempt operations, simplified or corrective invoices, withholdings or equivalence surcharge.
- Record timestamps use Europe/Madrid time.
- UI text is in English, following the repository language rule.

Not done, in rough priority order for the MVP:

1. Authentication, sessions and CSRF protection. The API is open; the server must stay on loopback until then.
2. AEAT integration: record XML, SOAP client with mTLS, submission state (in a separate insert-only table), mock (`m1`, `m2`).
3. Invoice PDF or printable view with the QR image and the Veri*factu legend.
4. Chained event log, required for the non-Veri*factu mode only; decide the mode first.
5. Expenses and received invoices, VAT books.
6. NIF check digits, customer directory, corrective invoices.
7. Backups (`b1`, `b2`) and deployment.

Not verified:

- CI has not run on GitHub (it triggers on pull requests and on `main`).
- The hash input format is verified against the AEAT examples, but nothing has been sent to the AEAT pre-production service.

## 2026-11-11: AEAT XML, client and mock; TypeScript in the web client

Author's instructions: go on with the record XML and the AEAT mock; the interface will be designed together later, because it helps to see which database entities are needed; the frontend must use jq79 + TypeScript (now a rule in `AGENTS.md`).

Done:

- `aeat/schemas`: unmodified official WSDL and XSD files, downloaded on 2026-11-11, with checksums and an XML catalog for offline validation.
- `crates/core`: `aeat::submission_request` builds `RegFactuSistemaFacturacion` with registration and cancellation records; `aeat::parse_submission_response` reads the response and SOAP faults. A test validates the request against `SuministroLR.xsd` with `xmllint` (required in CI, skipped locally when missing).
- `crates/aeat-mock`: library and binary. Validates the schema (optional), recomputes hashes, checks the chain per issuer, detects duplicates and injects faults (HTTP status, SOAP fault, garbage).
- `crates/server`: `aeat_client::AeatClient` (reqwest + rustls, optional PEM client identity), `store::chain_records`, and `config::aeat_endpoint`, which refuses endpoint overrides in production.
- End-to-end tests: invoices created through the API are loaded, sent by the client and accepted by the mock; tampered records and broken chains are rejected; each failure kind maps to its own error.
- Recipient and issuer NIFs must be exactly 9 characters, as the schema requires.
- Web client converted to TypeScript: `.ts` modules, API types in `web/src/types.ts`, `<script :setup lang="ts">` in `App.html`, strict `tsc --noEmit` as part of `npm run build`. Checked again in headless Chromium: no console errors.

- No software system (`SistemaInformatico`) or client certificate configuration yet.

Not verified:

- mTLS has not been exercised: the mock speaks plain HTTP.
- Types inside `App.html` are stripped by the jq79 plugin, not checked.

## 2026-11-11: Interface agreed; sign-in and automatic submissions

The author accepted the interface proposal and every recommended decision. They are kept in [`ROADMAP/2026-11-11/interface-and-entities.md`](../ROADMAP/2026-11-11/interface-and-entities.md).

Done:

- Migration `0002`: `users`, `sessions`, `events`, `aeat_submissions`, `aeat_submission_records`, `aeat_responses`, `aeat_record_results`. All insert-only except `users` and `sessions`.
- `auth`: Argon2id passwords (12 characters minimum); session token in a `__Host-session` cookie (`HttpOnly`, `Secure`, `SameSite=Strict`, 7 days), stored as SHA-256; CSRF protection with the `X-CSRF-Protection` header plus an `Origin` check; at most 5 failed sign-ins per user in 5 minutes (in memory). Every `/api` route except `/api/session` requires a session.
- `submission`: sends pending records in chain order, at most 1000 per request; stores the request before sending and the outcome afterwards; a rejected record blocks the queue. Background loop when `VERICOUNTS_AEAT_SUBMIT=1`, waiting what the AEAT asks and at least 60 seconds.
- API: `GET/POST/DELETE /api/session`, `GET /api/aeat`, `POST /api/aeat/submissions`; invoices and records carry their AEAT state.
- `vericounts-server create-user <username>`.
- Web client: sign-in and sign-out, AEAT state on invoices and records, queue warnings, in-page confirmation to cancel, all texts in Spanish in `web/src/i18n/es.ts` (rule added to `AGENTS.md`).
- Checked in headless Chromium against the real server, the mock with schema validation and submissions enabled: sign-in errors, validation message, issue, submission accepted, cancellation, cookie flags (not readable from JavaScript), sign-out. No CSP errors.

Known gaps:

- No second factor yet, and no screen to manage users or sessions.
- The failed sign-in limit is per process and is lost on restart.
- A record rejected by the AEAT can only be seen, not corrected: record correction is not implemented, so the queue stays blocked.
- If the process dies after sending and before storing the response, the records are sent again; how the AEAT reports such duplicates has not been handled.
- One submission runs at a time per process; running two server instances could send the same records twice.
- Still nothing sent to the real AEAT pre-production service, and mTLS not exercised.

Next, in the agreed order: settings (`company`, `series`), contacts, PDF with QR, record correction, home screen.

## 2026-11-11: Company, series and contacts

Done:

- Migration `0003`: `company` (single row), `series`, `contacts`; `invoices` gain `issuer_address`, `recipient_address` and `contact_id`.
- The issuer comes from `company`, not from environment variables (`VERICOUNTS_ISSUER_NIF` and `VERICOUNTS_ISSUER_NAME` are gone). Until it exists, invoice routes answer `409 company_missing` and the client opens Settings. The NIF is locked once a record exists, because it identifies the chain.
- Invoices are issued to a contact (`contact_id`) that is an active customer, in an existing active series. Name, NIF and address are copied into the invoice, so later edits do not change issued invoices.
- API: `GET/PUT /api/company`, `GET/POST /api/series`, `PUT /api/series/{code}`, `GET/POST /api/contacts`, `GET/PUT /api/contacts/{id}`. Series are never deleted or renamed, only described and switched off; contacts are archived, not deleted.
- Web client split into screens, each a jq79 component that receives `api`, `t` and `shell` (error reporting): `App.html` (session and bottom navigation), `Invoices.html`, `Contacts.html`, `Settings.html`. Error texts moved to `web/src/errors.ts`.
- Checked in headless Chromium from an empty database: first-run notice, company, series, contact, invoice with both addresses. No console errors.

Known gaps:

- A customer cannot be created from the new-invoice form; it has to exist in Contacts first.
- Contacts need a Spanish NIF; foreign customers are not supported.
- No sessions or users screen yet in Settings, and no AEAT section.

Next: printable invoice with QR, record correction ("subsanación"), home screen.

## 2026-11-11: Printable invoice with QR and home screen

Done:

- `GET /api/invoices/{id}/qr.svg`: QR code of the AEAT validation URL as SVG, error correction level M (`qrcode` crate).
- `GET /api/summary?year=&quarter=`: totals of a quarter (the current one by default) without cancelled invoices, with the breakdown per VAT rate.
- Web client: Home screen (quarter totals and what needs attention) and a printable invoice view with issuer, customer, lines, totals, the QR at 40 mm with the "QR tributario:" label and the Veri*factu legend, and a "cancelled" stamp. Printing uses the browser (`window.print()`), with print styles that hide the rest of the interface.
- Checked in headless Chromium: the view renders, a PDF was produced from it, and the QR decoded from the PDF at 300 dpi gives the expected validation URL.

Known gaps:

- The PDF is made by the browser; the server cannot produce one, so invoices cannot be emailed by the application.
- The invoice has no payment terms, due date, bank account nor logo.
- The Home screen has no input VAT nor form 303 result until expenses exist, and no backup status.

Open design question for the author: record correction ("subsanación"). Invoice data is insert-only, so correcting a rejected record needs a decision on what can be corrected and where the corrected data lives.

## 2026-11-11: Record corrections and both kinds of certificate

Author's decisions: start with corrections that resend the same data (no data changes yet), and support both certificates: the company's own and a personal one under a power of attorney.

Done:

- Migration `0004`: `billing_records.correction` and `previous_rejection` (`N`, `S`, `X`, the `RechazoPrevio` value). An invoice keeps exactly one original registration and may have any number of replacement records.
- `POST /api/invoices/{id}/correction`: adds a record that replaces the invoice's latest rejected record, with the same data. A registration is sent with `Subsanacion=S` and `RechazoPrevio=X` when the AEAT holds no registration of the invoice, or `S` when it holds one; a cancellation is sent with `RechazoPrevio=S`. The meaning of the values was taken from the documentation inside `SuministroInformacion.xsd`.
- New record state `superseded`: a rejected record replaced by a later record of the same invoice and type. Superseded records do not block the queue nor count in the state of the invoice.
- Requests can carry `Cabecera/Representante` (`VERICOUNTS_AEAT_REPRESENTATIVE_NAME` and `_NIF`).
- `certificate::inspect` reads the client certificate: holder, expiry, and the NIF it acts for (`organizationIdentifier` `VATES-…` for a company certificate, `serialNumber` `IDCES-…` for a personal one). `GET /api/aeat` reports it and whether it matches the company's NIF.
- The mock follows the chain across rejected records, checks corrections against what it holds, and can reject the records of a request on demand (`Fault::RejectRecords`, or `AEAT_MOCK_REJECT_FIRST` for the binary).
- Web client: "resend to the AEAT" on invoices with a rejected record, superseded and correction tags, and an AEAT section in Settings with the certificate status.
- Checked in headless Chromium with a personal certificate and a mock that rejects the first request: rejected state with its error, resend, accepted, and the certificate notice in Settings.

Not verified:

- Whether the AEAT requires `Representante` when a holder of a power of attorney submits, or accepts requests without it. It is optional in the schema; here it is sent only when configured.
- The subject attributes of real certificates. The parsing follows the usual FNMT conventions and was tested with generated certificates only.
- Real rejections: which errors can be fixed by resending the same data is unknown until records reach pre-production.

Known gaps:

- Corrections cannot change data. A record rejected because of wrong invoice data can only be resent as it is.
- Records accepted with errors cannot be corrected yet.
- `.p12` files must be converted to PEM by hand.
