# Code organised by domain

Author's instruction: organise all the code by domain. The aim: that the author can review it well.

## 2026-11-11: Five domains, the same on both sides

Domains: access (users, sessions, passkeys), company (company data, series), contacts, invoices (invoices, records, chain, modes, totals) and aeat (client, queue, practice mock, certificate). The same folders in `crates/server/src` and `web/src`; the map is in the README (Layout).

Done in five commits, each of one kind, so each can be reviewed on its own:

1. Server modules moved (`git mv`, so the diffs show renames). `directory.rs` split into company and contacts; `auth.rs` into `access/sessions.rs` and `access/users.rs`; `StoreError`, the event log and `Issuer`, used by every domain, to `error.rs`, `events.rs` and `company`. No logic changed; 75 tests pass as before.
2. `api.rs` split into each domain's `api.rs`: handlers moved unchanged; checked that the same 26 routes are registered, behind the same middleware.
3. Web client: files moved by domain, `types.ts` and `api.ts` split with their definitions unchanged; `app/api.ts` composes the same `api` object. Build (with type check) passes; all screens load in the browser through the real server.
4. Settings split into `CompanySettings`, `AccessSettings` and `AeatSettings`, each with its own state and loading; same templates. Checked in the browser: the sections show, saving the company and inviting work.
5. README map and a rule in AGENTS.md.

Decisions:

- Each domain folder: `mod.rs` describes what it holds and the tables it owns; `store.rs` data and rules; `api.rs` routes.
- `crates/core` already had one module per subject and is left as it is.
- `i18n/es.ts` and `mail/es.rs` stay single files, as AGENTS.md requires.
- Practice/live mode lives in invoices (it decides which invoices exist); aeat reads it.
- Integration tests renamed after their domain (`access.rs`, `company_and_contacts.rs`, `aeat_certificates.rs`, `aeat_modes.rs`); `roles.rs` and `security.rs` test shared code.

Next: the author asked that the interface not look like an invoice, and likes Revolut's style; the theme from [`2026-11-11.design-system`](2026-11-11.design-system.WIP.md) is to be redone.
