# Passwordless sign-in: email codes and passkeys

Replaces the password sign-in built in [`2026-11-11.invoices-mvp`](2026-11-11.invoices-mvp.WIP.md). Screen 9 and the user entities of [`ROADMAP/2026-11-11/interface-and-entities.md`](../ROADMAP/2026-11-11/interface-and-entities.md) were updated to match.

## 2026-11-11: Codes by email for sign-up and sign-in, passkeys, no passwords

Author's instructions: no passwords; always a one-time code sent by email, both to sign up and to sign in; passkeys to make it easier to use. Later in the session: use Mailpit to test SMTP.

Done:

- Migration `0005`: `users` loses `username` and `password_hash` and gains `email` (unique, lowercase), `webauthn_id` (random user handle for passkeys), `invited_by` and `activated_at`. New tables `login_codes`, `passkeys` and `webauthn_ceremonies`. Users from before the migration have no email, so it disables them; they must be invited again.
- Codes (`auth`): six digits, stored as SHA-256 of user id and code, valid for 10 minutes and once. Only the latest code of a user counts, with 5 guesses, each counted in the database before comparing, so parallel requests cannot try more. At most one code per minute and five per hour per user. `POST /api/session/code` always answers `202`, and mail is sent in the background, so neither the answer nor its timing tells whether an address has an account. The limits live in the database: they survive restarts and hold across instances (the in-memory throttle is gone).
- Sign-up: only invited addresses. The first user is invited with `vericounts-server invite <email>` (replaces `create-user`); signed-in users invite from Settings (`POST /api/users`), which emails an invitation. The first sign-in of an invited address is the sign-up (`activated_at`, event `user.signed_up`, `first_sign_in` in the answer). `DELETE /api/users/{id}` disables a user and closes their sessions; inviting the address again enables it.
- Passkeys (`passkeys`, webauthn-rs 0.6.2, pure Rust crypto): registration for the signed-in user (`POST /api/passkeys/options`, `POST /api/passkeys`) with user verification and a discoverable credential required; discoverable sign-in without email (`POST /api/session/passkey/options`, `POST /api/session/passkey`); list and remove (`GET /api/passkeys`, `DELETE /api/passkeys/{id}`). Challenges are stored in `webauthn_ceremonies` and deleted when answered, so each is used once; a registration can only be finished by the user who started it; pending sign-ins are capped at 1000. The relying party is the host of `VERICOUNTS_PUBLIC_URL` (default `http://localhost:8080`), which must be `https` outside `localhost` and cannot be an IP address.
- Mail (`mail`): SMTP with lettre and rustls (`VERICOUNTS_SMTP_URL`, `VERICOUNTS_MAIL_FROM`). Without SMTP, messages go to standard error, which is refused in production. Texts are in Spanish in `crates/server/src/mail/es.rs` (rule added to `AGENTS.md`).
- Web client: `SignIn.html` (email, code with resend countdown, "Entrar con passkey" button, passkeys in the email field's autofill, and an offer to create a passkey after a code sign-in when the user has none, with a welcome on sign-up); Settings gains "Tus passkeys" and "Usuarios" (invite, pending invitations, remove access). `web/src/webauthn.ts` converts WebAuthn options and answers between JSON and the browser API; component scripts cannot import modules, so it reaches the screens as a `webauthn` prop.
- Tests: codes (sign-up, single use, expiry, guesses, replacement, send limits, unknown and disabled addresses), CSRF, invitations and removal, passkeys end to end with a software authenticator in `tests/common/authenticator.rs` (registration, sign-in, single-use challenges, replayed answers, another origin, unknown and removed passkeys, disabled users, another user's ceremony), and a real SMTP test against Mailpit, required in CI (Mailpit service added to the workflow) and skipped locally without `VERICOUNTS_TEST_SMTP_URL` and `VERICOUNTS_TEST_MAILPIT_URL`.
- Checked in headless Chromium (mobile viewport) against the real server with the restricted role, SMTP to Mailpit and a CDP virtual authenticator: sign-up with a wrong and then the right code read from Mailpit, passkey created (resident), invitation received, sign-in by autofill and by the button, second user's sign-up. No console errors, no CSP violations.

Decisions taken, pending confirmation by the author:

- Sign-up is by invitation only. An open sign-up would give anyone who reaches the server full access to the books.
- Sign-up and sign-in are one screen and one flow; the first sign-in of an invited address creates the account.
- A passkey alone opens a session (it already requires user verification); the email code is the fallback and the way to add a passkey on a new device.
- Removing a passkey deletes its row; the event log keeps that it existed.
- Mail without SMTP goes to standard error outside production, so the server can be tried without a mail server.

Not verified:

- CI has not run with the Mailpit service; the image tag `axllent/mailpit:v1.33.1` matches the binary used here.
- Passkeys were only exercised with Chromium's virtual authenticator and the software authenticator of the tests, not with real devices (iOS, Android, password managers).
- No real SMTP provider has been tried, only Mailpit.

Known gaps:

- No screen to see or close open sessions.
- No roles: every user can invite and remove others.
- Expired `login_codes` rows are kept; they are few (at most five per user and hour).
