## 2026-11-11: build.yml, release.yml, setup.sh, Docker, Helm and a logo

Author's instructions: open the pull request; add `build.yml` (tests and builds, for main and pull requests) and `release.yml` (manual, input major/minor/patch: bump the version, run `build.yml`, create the GitHub release with the builds); a one-line `setup.sh` in the README with a wizard to install, reinstall/update (when it finds an installation) and uninstall; deployment with Docker and Helm; a logo from "vericounts" (verify + accounts) and blockchain + abacus.

Done:

- `build.yml` replaces `ci.yml`. Jobs: `test` (as before, plus shellcheck of the scripts and `helm lint`/`helm template`), `web`, `server` (static musl binaries on `ubuntu-latest` and `ubuntu-24.04-arm`) and `package`, which makes the release assets: `vericounts-<version>-<arch>-linux.tar.gz` (`bin/vericounts-server`, `web/`, `README.md`, `VERSION`), the packaged chart, `setup.sh` and `SHA256SUMS`. It runs on pull requests to main, pushes to main, and as a reusable workflow with a `ref` input.
- `release.yml`: manual from main; `scripts/version.sh <part>` bumps Cargo (workspace and lock file) and the chart; commits "Release vX.Y.Z" and pushes it with the tag to main; calls `build.yml` on the tag; creates the GitHub release with the assets and generated notes; pushes a multi-arch image to GHCR (`X.Y.Z`, `X.Y`, `latest`) built from the same archives with `docker/release.Dockerfile`.
- Docker: `Dockerfile` builds from source (web with Node, server with musl) into `gcr.io/distroless/static-debian12:nonroot`, about 25 MB; `docker-compose.yml` with PostgreSQL 16, a one-shot `migrate` service and the server on `127.0.0.1:8080`; `.env.example`.
- Helm: `charts/vericounts`, external PostgreSQL, migrations in an init container, one replica with `Recreate` (two instances would send the same records twice), Secret or `existingSecret`, optional ingress and AEAT certificate Secret, restricted security context. It refuses to render without SMTP in production.
- `setup.sh`: wizard and non-interactive actions; release download checked against `SHA256SUMS`; `/opt/vericounts/releases/<version>` with a `current` link, keeping the two previous versions; `/etc/vericounts/vericounts.env` (0640, root:vericounts) and `migrate.env` (0600, owner connection); hardened systemd unit; local PostgreSQL via apt or dnf, or an existing one. Uninstall keeps settings and database unless `BORRAR` is typed, after a warning about legal retention. Reinstalling over kept settings reuses them.
- Server: `healthcheck` subcommand (the distroless image has no curl) and `version`; empty environment variables count as unset (Compose passes unset settings as empty strings); `migrate` with `VERICOUNTS_APP_ROLE` makes the server's login role a member of `vericounts_app` (`grant_app_role`, tested).
- Logo: `web/public/logo.svg` (an abacus whose beads are chained blocks; the chain draws a check mark) and `logo-wordmark.svg` ("veri" in the brand blue, "counts" in the text colour, with a dark-mode colour). Used as the favicon, in the app header and in the README; the chart's icon points to it.
- Fixed while testing: in a browser without an authenticator that can keep passkeys, the background passkey autofill showed "Algo ha fallado" on the sign-in screen (`NotSupportedError`); it is now ignored there and shown as "no admite passkeys" on the button.

Found and worked around:

- Migration `0001` creates `vericounts_app` and catches only `duplicate_object`. PostgreSQL checks `CREATEROLE` before it sees that the role exists, so an owner without `CREATEROLE` fails even when the role was created beforehand. The migration cannot be changed (sqlx checks applied migrations' checksums), so the first migration needs an owner with `CREATEROLE`; the installer grants it for that run only and revokes it after.

Checked here:

- Image built from source (through a Docker Hub mirror and this sandbox's proxy CA, in a scratch copy of the Dockerfile) and run with the Compose file: migrations as the owner, membership granted, invite, code, sign-up, web client served; the server role cannot delete events.
- `setup.sh` in a Debian 12 container booted with systemd and PostgreSQL 15, with archives laid out like the release ones: unattended install, sign-up through the service, update to another version, the wizard through a terminal (detects the installation; reinstall; uninstall keeping data; install again reusing it, with the account still there; uninstall with `BORRAR`, which removes database, roles, user and settings).
- Helm chart: `helm lint` and `helm template` with and without the required values. Not installed on a cluster.
- shellcheck on every script; Rust tests, clippy, fmt and the web build; the browser check of sign-in and passkeys, with no console errors.

Not verified:

- No workflow has run on GitHub. In particular: the `ubuntu-24.04-arm` runner (may not be available to this repository), the GHCR push and its package permissions, the image tags of Mailpit and distroless, and pushing the release commit to main if main is protected.
- The aarch64 binary has not been built here.
- The installer was not tried with dnf, with an existing PostgreSQL, nor downloading from a real release (there is none yet).

## 2026-11-11: Project renamed to vericount

Author's instruction: the project is called vericount instead of vericounts.

Done:

- Renamed everywhere outside `RECORD/` and the applied migrations: crates (`vericount-core`, `vericount-server`, `vericount-aeat-mock`), binary `vericount-server`, environment variables `VERICOUNT_*`, chart `charts/vericount`, image `ghcr.io/jgermade/vericount` (now named explicitly in `release.yml` instead of after the repository), release archives `vericount-<version>-<arch>-linux.tar.gz`, installer paths (`/opt/vericount`, `/etc/vericount`), service, system user, database and roles (`vericount`, `vericount_owner`), interface and email texts, WebAuthn relying party name, logo wordmark ("veri" + "count").

Kept on purpose:

- The database role `vericounts_app`: migrations 0001 to 0003 create it and grant it its rights, and applied migrations cannot change (sqlx checks their checksums). Renaming it in a new migration is not safe either: roles belong to the whole PostgreSQL cluster, so databases sharing it (and the parallel test databases) would collide. The README says so.
- Links to the GitHub repository (`jgermade/vericounts`), which is its current name. If the repository is renamed, GitHub redirects the old URLs, release downloads included; `REPO` in `setup.sh` and the URLs in the README and the chart can then be updated.
- Existing records, which are append-only.

Checked again after the rename: Rust tests (with Mailpit, `CI=1`), clippy, fmt, web build, shellcheck, `helm lint`/`template`, the image built and run with Compose (sign-in code received), and `setup.sh` install, update and purge in the systemd container.

Observed once and not reproduced: in one of about 14 runs of the browser check, the last step (a second user's sign-up, right after the test removed Chromium's virtual authenticator) could not click "Enviarme un código" because the button kept being replaced. With tracing, and with or without a pause, 10 more runs passed. Not explained; worth watching on real devices.
